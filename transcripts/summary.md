# 技術會議摘要

## 一、技術討論要點

- **AI模型選型與整合策略：**
  - 目前核心分類任務採用 **GPT-4o** 大型語言模型，透過API進行呼叫。
  - 使用 **Chain-of-Thought (CoT) 推理**，要求模型展示完整的推理過程，以利追蹤決策邏輯及錯誤分析。
  - **Few-Shot Learning (少樣本學習)：** 將錯誤分類的範例加入 SYSTEM PROMPT 作為 Few-Shot 範例，建議至少提供 3-4 個，目標提升至 30 個以上。
  - **規則整合：** 建議將現有業務邏輯定義的「強硬規則」直接整合到 LLM 的輸入 Prompt 中。

- **資料流程與輸入結構：**
  - LLM 的輸入應包含客戶訊息、案件狀態和客戶記錄等所有相關背景資訊，形成整體性輸入。
  - 訊息中特定關鍵字不應直接觸發跳轉，而是需模型綜合判斷整個訊息的意圖和案例狀態。

- **系統架構設計考量：**
  - 提倡一體化處理，將所有分類邏輯和資料直接餵入 LLM 進行單一步驟的判斷。
  - 討論了基於訊息內容進行規則判斷可能導致誤判，新方案強調基於業務內部認定的「強硬規則」結合 LLM 的理解能力。

- **模型微調 (Fine-tune) 討論：**
  - 確認目前透過 API 使用的 GPT-4o 不支援直接微調。
  - 其他微調路線被提及作為研究或備選方案，但因其難度高且效果不佳，目前重心不在此。

- **效能評估與偵錯機制：**
  - 需追蹤 False Negative (FN) 與 False Positive (FP) 兩項關鍵指標，以精準評估模型表現。
  - CoT 的應用將使模型推理過程可被觀察，有助於找出錯誤發生的具體步驟。

## 二、系統與應用層決策

- **核心 AI 模型選用：** GPT-4o API
  - **決策依據：** 該模型具備強大的語言理解與分類能力，無需進行複雜的微調。

- **分類流程拍板：** 採用 LLM 一步到位的統一分類方案。
  - **決策依據：** 充分利用 LLM 整體理解上下文的能力，將所有判斷邏輯整合處理。

- **錯誤處理與持續優化：** 透過迭代修正 Prompt 方式優化模型。
  - **決策依據：** CoT 能提供錯誤根因分析，結合 Few-Shot 範例的補充，實現模型準確度的持續提升。

## 三、後續待辦與執行排程

- **Prompt 工程優化：**
  - **目標：** 整理並新增至少 30 個高質量 Few-Shot 範例至 SYSTEM PROMPT 中。
  - **指令要求：** 在 Prompt 中加入使用 Chain-of-Thought (CoT) 的指令。
  - **內容整合：** 確保所有相關規則、客戶訊息等關鍵資訊能正確傳遞給模型。

- **模型效能追蹤與驗證：**
  - **指標：** 收集和分析 False Negative (FN) 與 False Positive (FP) 數據。
  - **驗收標準：** 預期將分類準確率從 60G 提升至 80G。

- **迭代優化流程：** 建立常態性的錯誤案例分析會議，依據 CoT 推理過程調整 Prompt。

## 四、任務負責人 / 技術角色

- **AI 團隊 / ML Engineer：**
  - Prompt 設計、撰寫、驗證與迭代優化。
  - Few-Shot 範例的收集、整理與應用。
  - 模型效能數據的追蹤、分析與報告。
  - 分析 CoT 推理過程，定位錯誤根源並修正 Prompt。

- **業務團隊 / 數據標註人員（推估）：**
  - 提供業務層面判斷依據與「強硬規則」的詳細定義。
  - 協助對模型判斷錯誤的資料進行人工覆核與標註。

## 五、技術風險與挑戰

- **模型「黑箱」問題：**
  - **應對策略：** 強制使用 CoT，要求模型輸出推理步驟，增加透明度和可解釋性。

- **高質量 Few-Shot 範例的收集挑戰：**
  - **應對策略：** 投入資源進行範例的整理、標註與篩選，確保有效引導模型。

- **單一 LLM API 依賴：**
  - **應對策略：** 持續探索與評估備用方案，以降低潛在風險。

- **模型準確率提升的邊際效益遞減：**
  - **應對策略：** 結合 CoT 深入分析複雜案例，轉化為新的 Few-Shot 範例或更精確的 Prompt。

- **協作與知識傳遞：**
  - **應對策略：** 鼓勵各自探索 Prompt 優化路徑，最終以實際效果驗證。
