技術會議摘要
一、技術討論要點
•
AI模型選型與整合策略：
◦
目前核心分類任務採用 GPT-4o 大型語言模型，透過API進行呼叫12。
◦
強調使用 Chain-of-Thought (CoT) 推理：要求模型展示完整的推理過程，以利追蹤決策邏輯及錯誤分析1...。
◦
Few-Shot Learning (少樣本學習)：將錯誤分類的範例加入 SYSTEM PROMPT 作為 Few-Shot 範例，建議至少提供 3-4 個，目標提升至 30 個以上以顯著提升準確率13。
◦
規則 (Rule-based / LOW BASE) 整合： 建議將現有業務邏輯定義的「強硬規則」（LOW BASE 或 錄羅）直接整合到 LLM 的輸入 Prompt 中，而非作為獨立的前置處理步驟34。
•
資料流程與輸入結構：
◦
LLM 的輸入應包含客戶訊息、Case Status (案件狀態) 和 Cline Record (客戶記錄) 等所有相關背景資訊，形成一個整體性的輸入，以供模型進行全面判斷34。
◦
訊息中特定關鍵字（如 RIV）不應直接觸發跳轉，而是需模型綜合判斷整個訊息的意圖和案例狀態4。
•
系統架構設計考量：
◦
提倡 一體化處理：將所有分類邏輯和資料直接餵入 LLM 進行單一步驟的判斷，避免分階段處理可能導致的效率低下或依賴性問題2...。
◦
討論了先前基於訊息內容進行規則判斷可能導致誤判，因此新方案強調基於業務內部認定的「強硬規則」結合 LLM 的理解能力14。
•
模型微調 (Fine-tune) 討論：
◦
確認目前透過 API 使用的 GPT-4o 不支援直接微調2。
◦
儘管其他微調路線（如針對小型模型）被提及作為研究或備選方案，但因其難度高且目前效果不佳（即便全參數微調 SFT 亦不理想），故目前重心不在此12。
•
效能評估與偵錯機制：
◦
需追蹤 False Negative (FN) 與 False Positive (FP) 兩項關鍵指標，以精準評估模型表現3。
◦
CoT 的應用將使模型推理過程可被觀察，有助於找出錯誤發生的具體步驟，從而針對性地修改 Prompt23。
二、系統與應用層決策
•
核心 AI 模型選用： GPT-4o API12。
◦
決策依據： 該模型具備強大的語言理解與分類能力（目前效能約為 60G，期望透過優化達到 80G），且無需進行複雜的微調2。
•
分類流程拍板： 採用 LLM 一步到位 的統一分類方案2...。
◦
決策依據： 旨在充分利用 LLM 整體理解上下文的能力，將所有判斷邏輯（包括規則和訊息）整合處理，被認為是最正確且高效的方法34。
•
錯誤處理與持續優化： 透過迭代修正 Prompt 方式優化模型23。
◦
決策依據： CoT 能提供錯誤根因分析，結合 Few-Shot 範例的補充，將實現模型準確度的持續提升23。
三、後續待辦與執行排程
•
Prompt 工程優化：
◦
目標： 整理並新增至少 30 個高質量 Few-Shot 範例至 SYSTEM PROMPT 中，涵蓋正確與錯誤的分類情境13。
◦
指令要求： 在 Prompt 中明確加入使用 Chain-of-Thought (CoT) 進行思考和輸出推理過程的指令1。
◦
內容整合： 確保所有相關規則（LOW BASE）、客戶訊息、Case Status 等關鍵資訊能正確傳遞給模型34。
•
模型效能追蹤與驗證：
◦
指標： 需定期收集和分析 False Negative (FN) 與 False Positive (FP) 數據3。
◦
驗收標準： 透過上述優化，預期將分類準確率從目前的 60G 提升至 80G2。
•
迭代優化流程： 建立常態性的錯誤案例分析會議，根據 CoT 提供的推理過程，針對性地調整 Prompt，實現模型效能的逐步完善23。
四、任務負責人 / 技術角色
•
AI 團隊 / ML Engineer：
◦
Prompt 設計、撰寫、驗證與迭代優化1...。
◦
Few-Shot 範例的收集、整理與應用13。
◦
模型效能數據（FN/FP）的追蹤、分析與報告3。
◦
分析 CoT 推理過程，定位錯誤根源並修正 Prompt23。
•
業務團隊 / 數據標註人員（推估）：
◦
提供業務層面判斷依據與「強硬規則」的詳細定義4。
◦
協助對模型判斷錯誤的資料進行人工覆核與標註13。
五、技術風險與挑戰
•
模型「黑箱」問題： LLM 的內部推理過程相對不透明，難以直接理解其決策邏輯。
◦
應對策略： 透過強制使用 Chain-of-Thought (CoT)，要求模型輸出推理步驟，可大幅增加模型的透明度和可解釋性，便於定位錯誤環節並精準調整 Prompt1...。
•
高質量 Few-Shot 範例的收集挑戰： 模型的效能高度依賴於提供給 Prompt 的 Few-Shot 範例的數量與質量。
◦
應對策略： 需要投入資源進行範例的整理、標註與篩選，確保至少提供 30 個以上能有效引導模型的範例13。
•
單一 LLM API 依賴： 目前專案高度依賴 GPT-4o API，可能存在供應商服務穩定性、成本或政策變動的風險。
◦
應對策略： 團隊應持續探索與評估備用方案（如基於小型模型的微調），作為第二選擇，以降低潛在風險2。
•
模型準確率提升的邊際效益遞減： 隨著準確率的提升，進一步優化 Prompt 可能面臨效果遞減的挑戰。
◦
應對策略： 結合 CoT 深入分析複雜或持續出錯的案例，將其轉化為新的 Few-Shot 範例或更精確的 Prompt 指令，進行持續的迭代優化23。
•
協作與知識傳遞： 不同人員在 Prompt 優化中可能產生不同的想法和解決方案。
◦
應對策略： 鼓勵不同人員各自探索 Prompt 優化路徑，不需強制合併方案，最終以實際效果來驗證，這有助於多元化解決方案的探索2。
